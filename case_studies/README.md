# ParseAtlas Case Studies

A ParseAtlas **case study** is a directory that imports results from a real, external codebase and
subjects them to the same evidence discipline the internal experiments use. An experiment under
`experiments/` is generated by ParseAtlas and is reproducible from this repository. A case study
under `case_studies/` is not: its primary artifacts live somewhere else, and until they are
imported the case study holds a claim, not a result.

The directory therefore exists to make one distinction impossible to blur: **what was measured
here, and what was reported to us.**

---

## The two research modes

ParseAtlas runs two modes. They ask different questions, they admit different evidence, and only
one of them transfers to cryptographic code.

### Mode 1 -- Semantic exploration

```text
(E, G1) != (E, G2)
```

One token sequence `E` is interpreted under different grammars `G1`, `G2`, and the results are
**different mathematical functions**. Changing operator precedence changes what `2*x + 3` means;
the project has never claimed otherwise, and the root README states the point directly: the
research object is the pair `(token sequence, grammar)` rather than the token sequence alone.

What this mode studies: roots, degree, domains, singularities, periods, extrema, symmetries,
equivalence classes across the grammar space, and invariants that survive a grammar change.

What a result looks like here: experiments 0001 through 0023 -- for instance, the 24 precedence
grammars of `2*t + 1 - t/2` collapsing to 8 semantic classes.

**A speedup found in this mode is not an optimization.** If the candidate computes a different
function, it is faster at doing something else.

### Mode 2 -- Equivalence-preserving representation search

```text
R1(x) == R2(x)   for every x in the declared domain
Cost(R2) < Cost(R1)
```

Two representations `R1` and `R2` compute **the same value on the same declared domain**, and only
the measured cost differs. Nothing about the result is permitted to move -- not the value, not the
domain, not the undefined set.

What this mode studies: which representation transformations reduce measured cost, and which
structural quantity predicts that reduction.

What a result looks like here: a record conforming to
[`RECORD_SCHEMA.md`](RECORD_SCHEMA.md), carrying an equivalence argument, a randomized
differential test, edge cases, and a benchmark with its machine and repetition count.

## The modes must never be silently mixed

A document, a table, or a statistic that draws on both modes at once is invalid, because the two
modes disagree about what a "different representation" is allowed to do to the answer.

Concretely:

* A mode 1 finding may **not** be cited as evidence that a rewrite is safe. Mode 1 explicitly
  permits the function to change.
* A mode 2 record may **not** be filed without its equivalence proof obligation, even when the
  measured speedup is large. A large speedup with an unverified invariant is the most dangerous
  entry this repository can contain.
* A single statistic may **not** pool records from both modes. `transformation_statistics` refuses
  a record whose invariant is missing or pending, which makes the pooling structurally impossible
  rather than merely discouraged.

The root README states the rule this directory enforces:

> In cryptographic code, semantic reinterpretation that changes the result is not an optimization.

Only mode 2 transfers to cryptographic code. Mode 1 is how the project generates hypotheses about
which representation dimensions are worth searching; mode 2 is the only mode in which a
cryptographic claim can be made at all.

## Where the two modes meet

The connection between them is structural, not semantic, and it is the reason mode 1 is worth
running before mode 2.

Experiment 0021 measured that for a fixed token sequence the raw operation multiset --
`add`, `sub`, `mul`, `div`, node count -- is **invariant** across all 25 grammars, while the AST
critical-path depth is **not**: on `a/b + c*d - e/f + g` the same six operations
(`add` 2, `sub` 1, `mul` 1, `div` 2, across 13 AST nodes) arrange into dependency chains of depth
4 through 6, and only 4 of 25 grammars reach the minimum depth of 4.

The two counts are different quantities and are not interchangeable: **six** is the operation
count, the number of operator nodes the parse consumes; **thirteen** is the node count, which also
includes the seven leaves. It is the operation count that is invariant here, and the operation
count that the prediction below is about.

That is a statement about representation in general, not about precedence in particular. It
produces a falsifiable prediction for mode 2: if operation count is the quantity that does not
move when representation changes, then operation count is a poor candidate for predicting what
happens when representation changes, and dependency depth is a better one. Testing that prediction
against real benchmarks is the point of
[`ultrafast_secp256k1/benchmark_summary.md`](ultrafast_secp256k1/benchmark_summary.md).

## Evidence discipline

Case-study claims carry the evidence levels defined in
[`docs/research-methodology.md`](../docs/research-methodology.md):

1. **Observed** -- produced by a recorded execution.
2. **Symbolically justified** -- supported by an explicit rewrite, identity, or proof.
3. **Numerically validated** -- checked at declared sample points without singularities.
4. **Hypothesized** -- proposed as a pattern requiring broader testing.
5. **Benchmarked** -- supported by a documented performance measurement and environment.

Case studies add one intake level **below** all five:

* **Owner-reported** -- an external party stated the figure and ParseAtlas has executed nothing.

An owner-reported figure is a reason to import artifacts. It is not a result, it may not be
written into a measurement field, and `validate_record` rejects it from every statistic with that
reason stated explicitly. Promotion from `owner-reported` to `benchmarked` happens only by
importing the primary artifacts and re-deriving the number here.
