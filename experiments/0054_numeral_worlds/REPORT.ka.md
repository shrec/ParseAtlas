# ParseAtlas ექსპერიმენტი 0054: base, რომელშიც რიცხვია ჩაწერილი

## კითხვა, საიდანაც ეს დაიწყო — და მისი პასუხი

მფლობელმა ის პირველად დასვა, ერთი კვირით ადრე, ვიდრე მისთვის საჭირო ლექსიკა გაჩნდებოდა: შეადარე `2**50`-ის გამოთვლა decimal-ში იმავეს გამოთვლას binary-ში. აი პასუხი, როგორც **multiplication count**, აღებული emitted graph-ზე და translation-ის გარეშე.

```text
base  2    1125899906842624   51 digits,   1 nonzero    0 multiplications
base 10    1125899906842624   16 digits,  15 nonzero    7 multiplications
```

base 2-ში value-ს ზუსტად ერთი nonzero digit აქვს, ამიტომ მასზე გამრავლება არის shift და **არცერთი multiplication არ გამოიცემა** — numeral *არის* პასუხი, და მისი ჩაწერა თავად არის მთელი გამოთვლა. base 10-ში ასეთი სტრუქტურა არ აქვს, ამიტომ value უნდა აშენდეს, და მისი აშენების ყველაზე იაფი გზა არის addition chain. ამომწურავმა iterative deepening-მა მინიმუმი დააყენა **7** multiplication-ზე, გზით `1, 2, 4, 8, 16, 32, 48, 50`; `6` სიგრძის chain არ არსებობს, და ეს მოძებნილია და არა ციტირებული.

base-ებზე `2`-დან `120`-მდე გავლისას cost არის `0` ზუსტად მათგან `6`-ში — `2, 4, 8, 16, 32, 64`, ორის ხარისხებში — და `7` დარჩენილ `113`-ში. curve არ არის ტენდენცია. ის არის დანაწილება, და ის, თუ რომელ მხარეს მოხვდება რიცხვი, წყდება numeral world-ით და სხვა არაფრით.

## დაკვირვებული შედეგები

### 1. exactness არის base-ის და არა რიცხვის თვისება

`1/2` სრულდება base 2-ში და base 10-ში და მეორდება base 3-ში; `1/3` მეორდება 2-სა და 10-ში და სრულდება 3-ში; `1/10` სრულდება 10-ში და მეორდება 2-ში. predicate კლასიკურია — შეკვეცილი მნიშვნელის ყოველი მარტივი გამყოფი base-ს უნდა ყოფდეს — და ის შემოწმებულია ხელით გამოთვლილ შემთხვევებზე base `2`, `3`, `10` და `16`-ში, ორივე მიმართულებით.

| `3` | 1 | 6 | 2 | 22 | `1/100` `1/2` `3/5` `4/5` `298257223563/1000000000` |

**card-ის კითხვა A, ნაპასუხები: base 2 უარესია, ვიდრე base 10 თავად პროექტის constant-ებისთვის** — distinct constant-ებზე `6`-დან `1` `6`-დან `5`-ის წინააღმდეგ, ხოლო occurrence-ებზე `22`-დან `16` `22`-დან `20`-ის წინააღმდეგ. base 10 ზუსტად ერთ constant-ს კარგავს, `1/3`-ს, base 2 კი ხუთს.

**და არსებობს base, რომელშიც მათგან მეტია exact, ვიდრე base 10-ში: base `30`, სადაც სულ `6`-ვე exact-ია.** პასუხის ეს ნახევარი საერთოდ არ საჭიროებს sweep-ს და არავითარ bound-ს არ ატარებს. base `p/q`-ს exact-ს ხდის ზუსტად მაშინ, როცა `q`-ს ყოველი მარტივი გამყოფი მას ყოფს, ამიტომ base *ყოველ* corpus constant-ს exact-ს ხდის ზუსტად მაშინ, როცა ის მნიშვნელების უმცირესი საერთო ჯერადის radical-ის ჯერადია. ეს უმცირესი საერთო ჯერადი არის `3000000000`, მისი radical კი `30`, ამიტომ პასუხია **`30`, და ასეთი base-ების სრული სიმრავლე არის `30`-ის ყოველი ჯერადი.** sweep მას ადასტურებს; ის მას არ აწარმოებს.

**WGS 84-ის defining constant ამას დამოუკიდებლად წყვეტს.** სტანდარტი inverse flattening-ს აქვეყნებს როგორც `298.257223563`, ანუ `298257223563/1000000000`. ის exact-ია base 10-ში და base 30-ში, და inexact-ია base 2-ში და base 16-ში. დედამიწაზე ყოველი binary მანქანა, შესაბამისად, geodetic გამოთვლას დამრგვალებული ellipsoid-ით იწყებს, სანამ ექსპერიმენტი 0051-ის ერთი operation მაინც შესრულდება.

**base-ებზე გამავალი curve არ არის monotone, და მიზეზი ზუსტია.** ზოლში `2`-დან `120`-მდე exact count `43`-ჯერ ეცემა, როცა base ერთით იზრდება — ყველაზე თვალსაჩინოდ `6`-დან base `30`-ზე `0`-მდე base `31`-ზე. მეტი base მეტ exactness-ს არ ყიდულობს; მეტი *მარტივი გამყოფი* კი ყიდულობს. დაკვირვება ისაა, რომ count მხოლოდ radical-ის ფუნქციაა, `count(b) == count(radical(b))`, და ის მართალია გავლილი `119` base-იდან ყოველ ერთში.

**რაც ზოლს მიღმაა, ის ჩამოთვლილია და არა ღიად დატოვებული.** მნიშვნელობა შეიძლება ჰქონდეს მხოლოდ იმ მარტივ გამყოფებს, რომლებიც corpus-ის რომელიმე მნიშვნელს ყოფენ, და ეს სიმრავლეა `{2, 3, 5}`. ორი base, რომელთა signature ამ სიმრავლეზე ემთხვევა, ზუსტად ერთსა და იმავე corpus constant-ებს ხდის exact-ს, ამიტომ სულ ზუსტად `8` ქცევაა და არცერთ base-ს, რა ზომისაც უნდა იყოს, მეცხრის გამოვლენა არ შეუძლია. ზოლი უკვე შეიცავს თითო წარმომადგენელს თითოეულისთვის.

### 2. operation count მცდარია იმ გზით, რომელსაც base წყვეტს

პროექტი `x * 2`-სა და `x * 3`-ს ერთსა და იმავე ერთ multiplication-ს ახარჯავს. binary მანქანაზე პირველი არის shift, მეორე კი არა. კლასიფიკაცია ის სამმხრივია, რომელსაც card ითხოვს, პლუს identity, რომელიც საერთოდ არაფერს გამოსცემს.

```text
identity        the constant is 1                              0 operations
shift           the constant is a power of the base            1 shift
shift_and_add   every base digit is 0 or 1, t of them nonzero  t-1 shifts and t-1 additions
general         anything else                                  1 multiplication
```

გამოყენებული თავად corpus-ის multiplicative და dividing constant-ებზე — multiplier-ები `2 3 4 12 100` და divisor-ები `2 3 100`:

| base | identity | shift | shift_and_add | general |
|---|---|---|---|---|
| `2` | 0 | 2 | 3 | 0 |
| `3` | 0 | 1 | 2 | 2 |
| `6` | 0 | 0 | 0 | 5 |
| `10` | 0 | 1 | 0 | 4 |
| `16` | 0 | 0 | 0 | 5 |
| `30` | 0 | 0 | 0 | 5 |
| `60` | 0 | 0 | 0 | 5 |

**base 2 ერთადერთი base-ია probe set-ში, რომელსაც საერთოდ არ აქვს general multiplication**, და ის ამავე დროს ის base-ია, რომელიც exactness-ზე ყველაზე ცუდი იყო. numeral ღერძის ორი ნახევარი საწინააღმდეგო მიმართულებით ექაჩება, და ეს დაძაბულობა ამ card-ის ცენტრალური დაკვირვებაა და არა მასში არსებული უხერხულობა. base 16 — base, რომელშიც პროგრამისტი რეალურად წერს constant-ებს — მათგან არცერთს არ ხდის shift-ს, რადგან corpus-ის constant-ები პატარაა და `16` უხეშია.

ორი ხელით გადამოწმებადი მწკრივი მთელ ეფექტს ატარებს:

```text
(a + b) / 2     blind 1 addition and 1 division        base  2   2 cheap operations, no division
p * x / 100     blind 1 multiplication and 1 division  base 10   1 shift, 1 multiplication, no division
```

Montgomery form modular multiplication-ს აიაფებს და ამის საფასურს conversion-ზე იხდის, რაც სწორედ ის ფორმაა, რომელიც ექსპერიმენტმა 0042-მ notation-ისთვის ერთი დონით ზემოთ დააკვირვა. მოდელირებული როგორც operation count-ები სრული სიგანის multiplication-ებში, reduction price `r`-ით, რომელიც გავლილია და არა დეკლარირებული:

```text
classical modular multiplication    1 multiplication and 1 division-based reduction   =  1 + r
Montgomery modular multiplication   2 multiplications, and no division at all         =  2
conversion in                       1 Montgomery multiplication per operand           =  2 each
conversion out                      1 reduction step                                  =  1
```

ასე რომ, დაზოგვა არის `r - 1` თითო operation-ზე და ბაჟი არის `2` თითო შემომავალ operand-ზე პლუს `1` გამომავალზე, ანუ `5` ბინარული operation-ისთვის. crossover არის ამ ორის ფარდობა.

| reduction price | saving per operation | crossover in operations per crossing | პირველი მთელი chain, რომელიც იხდის | asymptotic ratio |
|---|---|---|---|---|
| `1` | 0 | არცერთი | არასოდეს | 1 |
| `2` | 1 | `5` | 6 | 3/2 |
| `3` | 2 | `5/2` | 3 | 2 |
| `4` | 3 | `5/3` | 2 | 5/2 |
| `6` | 5 | `1` | 2 | 7/2 |
| `8` | 7 | `5/7` | 1 | 9/2 |
| `12` | 11 | `5/11` | 1 | 13/2 |
| `16` | 15 | `1/3` | 1 | 17/2 |
| `24` | 23 | `5/23` | 1 | 25/2 |
| `32` | 31 | `5/31` | 1 | 33/2 |

**სად ჩერდება მტკიცება, ეს მასთან ერთადაა გაცხადებული.** reduction price `1`-ზე — division, რომელიც არა უმეტეს multiplication-ისა ღირს — დაზოგვა არის `0` და crossover საერთოდ არ არსებობს არცერთ chain სიგრძეზე. Montgomery form-ის მთელი მოტივი division-ის ფასია, და მოდელი ამას ამბობს და არა უბრალოდ გულისხმობს. ფასზე `8` ეს ფორმა იხდის თავს თითო crossing-ზე ერთი modular multiplication-ითაც კი.

word დონეზე ინსტანცირება ცვლის ერთეულებს და არა crossover-ს: `k`-word operand-ებით ბაჟი არის `5` გამრავლებული `k**2`-ზე word multiplication, რაც `k`-ს `64`-ზე არის `20480`, და crossover არის ფარდობა, რომელმაც არ იცის, რამდენად ფართოა modulus.

**ახლა ის შედარება, რომელსაც card ითხოვს, და სწორედ ეს ღირს იმაზე მეტი, ვიდრე თითოეული რიცხვი.** სამივე seam, რომელიც ამ პროექტმა დააფასა, ერთ მოდელში თავსდება:

```text
gain(n) = n * saving - toll          crossover at   n* = toll / saving
```

| seam | saving per operation | toll per crossing | crossover | ხელმისაწვდომი operations per crossing |
|---|---|---|---|---|
| Montgomery form, reduction price `6` | 5 | 5 | `1` | თავისუფალი |
| Cartesian to polar, roadmap-ის შესწორებული ციფრი | 3 | 4 | `4/3` | თავისუფალი |
| 0042 Model II, named intermediates | `11/29` | 1 | `29/11` | `1`, დაფიქსირებული splitting rule-ით |

**ეს ორი seam ერთნაირად არ იქცევა, და ალგებრა ამის მიზეზი არ არის — ის იდენტურია.** Montgomery form-ში და polar conversion-ში operations per crossing არის პროგრამის თავისუფალი პარამეტრი: აწიე chain და ბაჟი ამორტიზდება, რაც ზუსტად roadmap-ის ის შესწორებაა, რომ გადამწყვეტი სიდიდე არის operations per boundary crossing და არა chain-ის სიგრძე. 0042 Model II-ში ეს პარამეტრი **დაფიქსირებულია `1`-ზე splitting rule-ით**: ყოველი fragment ზუსტად ერთხელ იკვეთება და ზუსტად საკუთარ შიდა bracket-ებს იძლევა, ამიტომ არქიტექტურას curve-ზე აღმა სვლა არ შეუძლია, რაგინდ გრძელიც გახდეს დოკუმენტი. მისი break-even საკუთარი გამოქვეყნებული ციფრებიდან აღდგება როგორც `11/29`, ანუ `0.3793103448275862` bracket წყვილი თითო naming ერთეულზე, ხოლო crossover, რომელიც მას დასჭირდებოდა, არის `29/11` fragment-ის ღირებულების პრიზი თითო crossing-ზე.

ასე რომ, 0042-ის ვერდიქტი არასოდეს ყოფილა რიცხვი, რომელსაც უფრო დიდი corpus გადაძრავდა. **seam გადასახდელია მაშინ, როცა პრიზი იზრდება იმასთან ერთად, რასაც პროგრამა აკონტროლებს, ბაჟი კი არა.** Montgomery form-ისთვის ის ასეა; fragment routing-ისთვის კი არა.

## ინტერპრეტაცია

**numeral ღერძი რეალურია და ის სხვა ორის დაზუსტება არ არის.** ის 25 world-ის ranking-ს ხელუხლებელს ტოვებს — დამტკიცებადად და არა შემთხვევით — და corpus-ს computation cost-ით ისე გადაალაგებს, რომ ეს დამოკიდებულია იმაზე, რომელ base-ს იყენებს მანქანა. ეს ერთი და იმავე ობიექტების ორი სხვადასხვა დალაგებაა, და ეს card არის ის ადგილი, სადაც პროექტს პირველად ორივე უჭირავს.

**პროექტის საკუთარ operation count-ში base არის ჩაშენებული, და ის base 2 არ არის.** ყოველი `*`-ისთვის ერთი multiplication-ისა და ყოველი `/`-ისთვის ერთი division-ის დახარჯვა ზუსტად სწორია base `5`, `6`, `8`, `16`, `30` და `60`-ისთვის ამ corpus-ზე, და არასწორად აფასებს `5565` წყვილიდან `515`-ს base 2-ისთვის. count-ში როგორც notation-ში არაფერი იყო მცდარი; ის იყო ციტირებული როგორც computation.

**equivalence ხაზს აქვს ადგილმდებარეობა.** ალგებრული equivalence და რიცხვითი equivalence literal-ზე იშლება და არა operation-ზე. input-ებზე, რომლებსაც binary მანქანა ზუსტად ინახავს, `15` ალგებრულად იდენტური წყვილი `120`-დან `2`-ჯერ არ თანხმდება; input-ებზე, რომლებსაც ის ამრგვალებს, იგივე წყვილები `65`-ჯერ არ თანხმდებიან. roadmap-ის მესამე სტანდარტი, შესაბამისად, არ არის ასარჩევი tolerance — ის კითხვაა იმაზე, თუ რომელი numeral world-იდან მოვიდა input-ები.
