## მიზანი

Owner-მა ეს card დააყენა 2026-09-05-ს:

> *"The point is to arrange the dataflow for the processor according to different representations so
> you can SEE which is more efficient. And formulas are good, but hardware often has hidden parts
> that do not match the formulas, and sometimes on real hardware a different representation becomes
> the profitable one."*

ეს პროექტი გამოსულ ხეზე სამ სტრუქტურულ სიდიდეს ზომავს — operation count (`canonical.operation_cost`,
card 0021), critical-path depth (`parallel_worlds.depth`, card 0041) და peak live values
(`memory_ceiling.peak_live`, card 0044). **ისინი მოდელია, და hardware ამ მოდელს სიტყვასიტყვით არ
ახორციელებს.** ეს card ზომავს, სად არ თანხმდებიან მოდელი და მანქანა, C-ს გამოშვებით, კომპილაციითა და
გაშვებით. სამივე საზომი იმ card-იდან არის იმპორტირებული, რომელსაც ის ეკუთვნის, და არცერთი არ არის
ხელახლა დაწერილი; ტესტები ამას identity-ით ამოწმებენ და არა equality-ით.

## რა იწერება და რა იზომება

**გამოსული ფორმა დასახელებული temporary-ების თანმიმდევრობაა, თითო operation თითო C statement-ზე, და არა
ერთი ჩალაგებული expression.** სამი მიზეზი, და მესამე წყვეტს:

- მოდელთან შესაბამისობა შესამოწმებელია — თითო statement თითო შიდა ხის კვანძზე, ასე რომ მკითხველი
  მოდელის operation-ებს სტრიქონების დათვლით ითვლის და არა parenthesisation-ის ნდობით;
- გამოსული რიგი თავად ხის post-order-ია, ასე რომ C source dataflow graph-ის ტრანსკრიპტია და არა
  სტრიქონი, რომელსაც C compiler-ის precedence-ს ხედ უნდა დაეშალა;
- clang-ის default C-ში არის `-ffp-contract=on`, რომელიც multiply-სა და add-ს მხოლოდ ერთი statement-ის
  შიგნით აერთიანებს. თითო operation თითო statement-ზე ამიტომ fusion-ს default-ად გამორთულს ტოვებს, და
  `-ffp-contract=fast` არის ის flag, რომელიც მას statement-ებს შორის უშვებს. Fusion ხდება
  ექსპერიმენტის დეკლარირებული ღერძი და არა შემთხვევითობა იმისა, როგორ ჩაიწერა expression — თუმცა ეს
  flag დამოუკიდებლად ინერტული აღმოჩნდა, იმ მიზეზით, რომელიც ქვემოთ optimisation-ის კიბეზეა გაზომილი.

ორი რეჟიმი იზომება, რადგან მოდელი ორ სხვადასხვა პროგნოზს აკეთებს და ერთი loop ორივეს ვერ შეამოწმებს:

- **throughput** — expression-ის ოთხი დამოუკიდებელი ასლი თითო loop step-ზე, ოთხი accumulator, ყოველი
  input წაკითხული ცხრილიდან loop counter-ით. მომდევნო step-ები დამოუკიდებელია, ასე რომ ზღუდავს ის,
  რამდენი operation გამოიცემა. ეს ის რეჟიმია, რომელიც operation count-ს უნდა ეპროგნოზებინა.
- **latency** — ერთი accumulator, და წინა step-ის შედეგი ერთ input-ში დაბრუნებული `acc * 1e-18`-ით.
  მომდევნო step-ები ვერ გადაფარავენ ერთმანეთს, ასე რომ ზღუდავს დამოკიდებული operation-ების ყველაზე
  გრძელი ჯაჭვი. ეს ის რეჟიმია, რომელიც depth-ს უნდა ეპროგნოზებინა.

**Feedback ერთ input-ში მიდის და არა ყველაში, და მიზეზი ის დეფექტია, რომელიც ამ card-მა საკუთარ პირველ
harness-ში აღმოაჩინა.** როცა ერთი და იგივე შეშფოთება ყველა input-ს ემატება, ორი ცვლადის გამოკლება მას
ზუსტად აბათილებს — `(x + fb) - (h + fb)` არის `x - h` — და `-ffast-math`-ზე clang სწორედ ამ გაბათილებას
ასრულებს, რის შემდეგაც loop-ში არაფერია accumulator-ზე დამოკიდებული და compiler loop-ს შლის. ასეც
მოხდა: წრის centre-radius writing `O3fast`-ზე `0.00` წამს ზომავდა თითო step-ზე, სანამ harness არ
შეიცვალა. შესწორებული harness ფესვიდან ყველაზე შორეულ ცვლადის ფოთოლს კვებავს, და audit ადასტურებს, რომ
ეს ფოთოლი ხის სრულ depth-ზე ზის ამ card-ის მიერ კომპილირებული ყველა `42` writing-ისთვის, ასე რომ
გაზომილი ჯაჭვი სწორედ ის ჯაჭვია, რომელსაც მოდელი ასახელებს.

**როგორ არის optimiser-ისთვის აკრძალული სამუშაოს წაშლა**, რადგან benchmark, რომელიც ცარიელ loop-ს ზომავს,
სწორედ აქ არის კლასიკური მარცხი:

- ყოველი input იკითხება ცხრილიდან loop counter-ით ინდექსირებულად, ასე რომ expression-ის არცერთი ნაწილი
  არ არის loop-invariant და ვერცერთი ვერ გატანილა loop-იდან;
- ყოველი loop step-ის შედეგი გროვდება;
- accumulator იწერება caller-ის მფლობელობის pointer-ით, ემატება checksum-ს, ინახება `volatile
  double`-ში და იბეჭდება, ასე რომ ეს დაკვირვებადი ქცევაა, რომლის მოცილებაც C standard-ს compiler-ისთვის
  აკრძალული აქვს.

ეს guard გაზომილია და არა ნაგულისხმევი. იმავე `34` kernel-ის მეორედ კომპილაცია accumulator-ის მოხსნით
ყოველი მათგანისთვის იძლევა გაზომილ ბლოკს `0.0` ნანოწამზე თითო step-ზე, guard-ით კი `0.3601`-დან
`1.3699` ნანოწამამდე თითო step-ზე — თანაფარდობა `0.000000`. Loop guard-ის გარეშე უბრალოდ უფრო სწრაფი კი
არა, არამედ გამქრალია. მეორე სიგნალიზაცია უარს ამბობს ნებისმიერი run-ის დალაგებაზე, რომელშიც გაზომილი
ბლოკი `10` timer tick-ზე მოკლე დაბრუნდა.

### 1. სისწორე, ნებისმიერ timing-ამდე

ყოველი გამოსული ფუნქცია, რომელსაც ეს card კომპილირებს — `34` corpus writing და `8` probe writing —
ზუსტ რაციონალურ oracle-თან, `8` დეკლარირებულ input row-ზე, ოთხივე level-ზე: `336` შემოწმება თითო
level-ზე, სულ `1344`, `0` მარცხი. ყველაზე დიდი დაკვირვებული ფარდობითი გადახრა არის `2.5975e-15`,
დეკლარირებული tolerance-ის `1e-09` წინააღმდეგ — ექვსი რიგით მარაგი. Oracle მთლიანად `Fraction`-ს
იყენებს და არაფერს ამრგვალებს, ასე რომ ეს გადახრა მთლიანად მანქანის floating-point დამრგვალებაა და
არცერთი ნაწილი არ არის oracle-ის.

**და ეს audit შეიძლება ჩავარდეს, რაც პირველმა რედაქციამ არასოდეს აჩვენა.** ტესტი, რომელიც სწორედ ამ
საქმისთვის იყო დასახელებული, აგებდა *სწორ* writing-ს და ამტკიცებდა, რომ audit გაიარა; იზოლირებულ
ასლზე audit-ის ორნაირად გატეხვამ მისი ყველა `65` ტესტი მწვანედ დატოვა. კონტროლი ახლა ცვლის emitter-ს
ისეთით, რომელიც წერს `b - a`-ს იქ, სადაც writing `a - b`-ს ამბობს, და მოითხოვს, რომ audit-მა
დააბრუნოს `all_match is False` არაცარიელი წარუმატებლობის სიით, რომელიც kernel-ს ასახელებს — ზუსტად იმ
გზით, საიდანაც ამ აბზაცის `0` წარუმატებლობა მოდის. მეორე კონტროლი audit-ს ჩააგდებინებს და მოითხოვს,
რომ report-მა გამონაკლისი ააგდოს ნებისმიერი benchmark-ის დაწყებამდე. იხილეთ **ვალიდაცია**.

### 2. გამეორებების sweep და noise floor

გამეორებების რაოდენობა swept-ია და არა დეკლარირებული. `4096`-დან `4194304` loop step-მდე თითო გაზომილ
ბლოკზე, `41` ბლოკით თითო kernel-ზე:

```text
loop steps   ns per step   block (ms)   ticks   p10-p90 band, median   p10-p90 band, max
      4096        0.5615       0.0023      23                 39.88%              55.56%
     16384        0.5219       0.0086      86                 34.28%              72.29%
     65536        0.4066       0.0266     266                 49.30%              74.46%
    262144        0.4118       0.1079    1080                 14.92%              62.42%
   1048576        0.4302       0.4511    4511                 27.03%              52.34%
   4194304        0.4371       1.8332   18332                 40.00%              84.60%
```

მიმდევრობითი drift წამი-თითო-step-ზე მაჩვენებელში ამ გაშვებისთვის: `7.07%`, `22.08%`, `1.27%`,
`4.47%`, `1.59%`.

**Drift ამ report-ის ყველაზე ხმაურიანი სიდიდეა, ის ქვეყნდება და არა მტკიცდება, და ეს შესწორებაა.**
`2` წინა რედაქციამ მასზე ტესტი ააგო. პირველი ამტკიცებდა, რომ მრუდი მონოტონურად ბრტყელდება, რაც არ
ხდება. მეორემ ეს ჩაანაცვლა ზღურბლით: `262144`-ზე და მის შემდეგ `3` drift-იდან მინიმალური უნდა
დაცემულიყო `8%`-ზე დაბლა — რიცხვი, არჩეული სწორედ იმ უდიდესის მიღმა, რომელიც `17` sweep-მა გადმოსცა.
Review-მ ამ card-ის ფაილი `5`-ჯერ გაუშვა და ნახა, როგორ ჩავარდა ეს ტესტი მათგან `1`-ში, `8.53%`-ზე
დეკლარირებული `8%`-ის წინააღმდეგ — იმ გაშვებაზე, რომელიც `5`-იდან მეორე ყველაზე სწრაფი იყო, ასე რომ
წარუმატებლობა კონკურენცია არ იყო.

**ციფრები მცდარი არ იყო; მცდარი იყო მათგან გამოტანილი დასკვნა.** Manager-მა იგივე სიდიდე ხელახლა
გამოიყვანა `12` sweep-ზე და მიიღო უარესი `2.61%` და მედიანა `0.25%`, რაც დეკლარირებულს ეთანხმება. აქ
ხელახლა გაზომილი `48` sweep-ზე, იმ ფანჯარაში, როცა იმავე მანქანაზე `2` სხვა card აკომპილირებდა, იგივე
სიდიდე მერყეობს `0.06%`-დან `11.43%`-მდე მედიანით `1.82%`; ის აღემატება ადრე დეკლარირებულ უარეს
`2.82%`-ს `48`-იდან `17`-ში და კვეთს `8%`-ს მათგან `3`-ში. Sweep-ის შიგნით ცალკეული drift-ები
მერყეობდა `0.00%`-დან `73.13%`-მდე მედიანით `5.56%`, და `48`-იდან `2` ატარებდა შუალედურ drift-ს
`50%`-ზე მაღლა.

**წესი, რომელიც აქედან დაიბადა და რომელიც ამ card-ს სცდება: არ დაახარო ტესტი სტატისტიკაზე, რომლის
შემოსაზღვრაც ვერ ხერხდება — გამოაქვეყნე ის თავისი განბნევით.** სელექციის მაქსიმუმიდან გამოთვლილი
ზღვარი ზღვარი არ არის, და შერჩევის გაზრდა მას ზღვრად არ აქცევს; ის მხოლოდ ავადებს ცდომილებას.
ზღურბლი წაიშალა და არ აიწია, ზემოთ მოცემული ციფრებია შედეგი, და ტესტი ახლა ამტკიცებს მხოლოდ იმას, რაც
არჩევანში დეტერმინირებულია: რომ `262144` არის swept მრუდის წერტილი, რომ ის არ არის ბოლო წერტილი, და
რომ გაზომილი ბლოკი გამეორებების რაოდენობასთან ერთად იზრდება. ეს ბოლო მონოტონური დამოკიდებულებაა
INPUT-ში და არა ხმაურში — step-ების რაოდენობა მიმდევრობით წერტილებს შორის ოთხხდება — და იგი ძალაში
იყო `48` sweep-იდან `48`-ში, ბლოკის ზრდით ბოლოდან ბოლომდე `551`-დან `1191`-მდე, იმ `1024`-ის
წინააღმდეგ, რასაც step-ების რაოდენობა დამოუკიდებლად იძლევა.

Timer `262144`-ზე წყვეტს შეზღუდვას, სადაც ბლოკი `1080` tick-ია; უფრო გრძელი ბლოკები არაფერს
ყიდულობენ და interference-ს აგებენ, ასე რომ `262144` არის მრუდიდან წაკითხული წერტილი. მოკლე ბოლოზე ბლოკი თავად timer-ის გარჩევადობაზეა — sweep-ის პირველი
წერტილი `9` tick-მდე დაბალიც დაბრუნებულა — და სწორედ ამიტომ არ იკითხება რაოდენობა იქიდან.

**Noise floor გაზომილია და არა ნავარაუდები.** ყოველი მოხსენებული run თითო object-ისთვის ატარებს მისი
writing-ებიდან ერთის მეორე ასლს, byte-იდენტური C-დან კომპილირებულს, ასე რომ ორს შორის ნებისმიერი სხვაობა
კონსტრუქციით noise-ია. მოხსენების run-ში `128` ასეთ წყვილზე:

```text
median   0.242%
p90      1.298%
p95      2.062%
maximum 14.867%
```

ეს ერთი გაშვებაა. განყოფილება `5`-ის შვიდ survival გამეორებაზე, რომლებიც იმავე დუბლიკატებს ატარებენ,
მედიანური იდენტურ-kernel-იანი სხვაობა იყო `0.751%`, ხოლო ყველაზე ცუდი `14.398%` — ასე რომ ფორმა
სტაბილურია, თუნდაც ცალკეული ციფრები არ იყოს.

დეკლარირებული floor არის p95, `2.062%`, და არა მაქსიმუმი. განაწილება ძლიერ ასიმეტრიულია, და ერთმა run-მა,
რომელიც მაშინ იყო აღებული, როცა იმავე მანქანაზე სამი სხვა job კომპილირდებოდა, ერთი გადახრა `19.04%`
მოგვცა; იმავე level-ისა და რეჟიმის სამჯერ გაშვებამ მშვიდ მანქანაზე მაქსიმუმები `1.17%`, `2.39%` და
`1.75%` მოგვცა. მაქსიმუმის აღება ერთ preempted ბლოკს მთელი ექსპერიმენტის გარჩევადობის დაყენების უფლებას
მისცემდა. აქ არაფერი ეყრდნობა ამ არჩევანს: floor swept-ია `0`-დან `20%`-მდე და მრუდი `7` სექციაშია
გამოქვეყნებული.

### 3. Harness-ის იატაკი

Kernel, რომელშიც არითმეტიკა საერთოდ არ არის — ის ერთ მნიშვნელობას კითხულობს და აგროვებს — loop-ის
საკუთარ ფასს იძლევა. გაზომილი ყოველ level-ზე, `1`, `2`, `4`, `8`, `16` და `32` ფოთლის ბალანსირებულ
ჯამებზე:

ეს timing-ის გაზომვაა, ამიტომ ის სამ წაკითხვაზე დიაპაზონად არის მოცემული და არა ერთ რიცხვად:

```text
level          throughput, zero-operation kernel   latency, zero-operation kernel
O0                        1.0262 ns - 1.7952 ns             5.1300 ns - 5.6671 ns
O2                        0.2563 ns - 0.2567 ns             1.8616 ns - 2.0008 ns
O2nativefma               0.2331 ns - 0.3231 ns             0.9094 ns - 0.9529 ns
O3fast                    0.2178 ns - 0.2277 ns             0.9094 ns - 0.9117 ns
```

`O2`-ზე ექვს წერტილზე გავლებული least-squares წრფე throughput რეჟიმში იძლევა intercept-ს `0.1536`-დან
`0.1553` ნანოწამამდე და slope-ს `0.0604`-დან `0.0610` ნანოწამამდე თითო operation-ზე, ხოლო latency
რეჟიმში intercept-ს `1.8048`-დან `1.9090` ნანოწამამდე და slope-ს `1.0410`-დან `1.1327` ნანოწამამდე
თითო depth დონეზე. Latency-ის წრფე depth-ის მიმართ არის მორგებული და არა operation count-ის მიმართ,
რადგან ესენი ბალანსირებული ჯამებია, რომელთა depth მათი operation count-ის ლოგარითმივით იზრდება;
არასწორი ცვლადის მორგება slope-ს უაზროს გახდიდა.

**`O3fast`-ზე latency-ის მორგება ფასად საერთოდ არ არის მოყვანილი, და მიზეზი შედეგია.** `-ffast-math`
ბალანსირებულ ჯამს reassociate უკეთებს, ასე რომ მისი შესრულებული depth მისი ხის depth არ არის, და
least-squares წრფე **უარყოფითი** intercept-ით ბრუნდება — `-3.6215`-დან `-3.5302` ნანოწამამდე სამ
წაკითხვაზე, ასე რომ ნიშანი ერთი გაშვების არტეფაქტი არ არის. მორგება, რომელიც დადებითიც კი ვერ ხდება,
ყველაზე ნათელი ცალკეული ნიშანია იმისა, რომ მოდელის depth-მა ამ level-ზე მანქანის შესრულებულის აღწერა
შეწყვიტა.

Overhead ერთნაირად ემატება object-ის ყოველ writing-ს, ასე რომ მას ვერ შეუცვლია, რომელი writing არის
უფრო სწრაფი, მაგრამ ის ამ მოხსენების ყოველ ფარდობით სხვაობას კუმშავს. ყოველი აქაური სხვაობა ქვედა
ზღვარია იმ სხვაობისა, რომელიც თავად ორ dataflow graph-ს შორისაა.

### 4. რა გადარჩება compiler-ს, ინსტრუქციებში დათვლილი

ინსტრუქციების დათვლა ხმაურიანი არ არის. ყოველი writing ცალკე ფუნქციად კომპილირდება, assembly უკან
იკითხება, და ერთი object-ის ორ writing-ს, რომლებიც mnemonic-ების ერთსა და იმავე multiset-ად
კომპილირდება, სხვაობა წაშლილი აქვს:

```text
level         objects whose writings compile to identical instructions
O0                 3 of 16
O2                 0 of 16
O2nativefma        0 of 16
O3fast             8 of 16
```

`O3fast`-ზე ის რვა არის `binomial_square`, `difference_quotient`, `distributive_law`, `line`,
`linear_approximation`, `product_chain_8`, `sum_chain_8` და `trapezoid_area`. `O0`-ზე ის სამი არის
`perfect_square_trinomial`, `product_chain_8` და `sum_chain_8` — ის object-ები, რომელთა ორ writing-ს უკვე
ერთი და იგივე operation multiset აქვს ერთსა და იმავე რიგში.

იმავე assembly-ს პასუხობს მეორე კითხვაც, რომელშიც noise floor არ არის: რამდენი writing მოათავსა
compiler-მა vector register-ში და როგორ იყოფა გამრავლების რაოდენობა სკალარულ და packed ფორმებად.
Writing ითვლება ვექტორიზებულად, როცა ის ატარებს სულ მცირე ერთ packed არითმეტიკულ ინსტრუქციას —
packed add, subtract, multiply ან divide — განსხვავებით მათ ირგვლივ არსებული packed გადაადგილებისგან:

```text
level          writings vectorised, of 34   scalar multiplies   packed multiplies
O0                                      0                  93                   0
O2                                      8                  66                  10
O2nativefma                             2                  54                   0
O3fast                                  1                  46                   0
```

**ჩვეულებრივი `-O2` არის ის საფეხური, რომელიც ამ corpus-ს ვექტორიზებს**, და მის ზემოთ `2` საფეხური

მტკიცება მუშაობდა, და არც იმ უჯრებს არჩევს, რომელთა შესარჩევადაც გამოიყენეს. მიზეზი ჩანს ამ card-ის საკუთარ დამატებით
საზომში: ტოლი operation-ებისა და ტოლი depth-ის დროს უფრო მაღალი peak-ის მქონე ფორმას schedule width
`17` აქვს `9`-ის წინააღმდეგ, ასე რომ ის თითქმის ორჯერ მეტ operation-ს სთავაზობს გასაშვებად თავის
ყველაზე დატვირთულ ნაბიჯზე. `peak_live`-ის მინიმიზაცია ამ სიდიდეებზე უფასო არ არის; ის ოდნავ მავნეა.

### 10. განმეორებადობა: რომელ უჯრებს აქვს საერთოდ გაზომილი რიგი

Probe-ების ნაკრები `5`-ჯერ გაეშვა, თავიდან ბოლომდე, და თითოეული უჯრის ყველაზე მცირე და ყველაზე
დიდი სხვაობა ჩაიწერა. **`32` უჯრიდან `25`-მა ხუთივე გაშვებაზე ერთი და იგივე დაკვირვება დააბრუნა;
`7`-მა არა.** მეორე ხუთგაშვებიანმა კვლევამ, მხოლოდ მიმართულებით შეფასებულმა და floor-ის უგულებელყოფით,
`32`-იდან `24` თანხმობაში დააყენა. ყველაზე ფართო დიაპაზონი, რომელიც ერთმა უჯრამ დაფარა, არის `40.51`

**`1%`-სა და `100%`-ს შორის არცერთი ცალკეული ზღურბლი ორჯერ ერთნაირად არ ალაგებს ამ მანქანაზე ყველა

### 11. Peak live-ის ზღვარი

Swept და არა ნავარაუდები, `8` ფოთლის რაოდენობაზე, თითოეულზე იმ depth-ის აღებით, სადაც `peak_live`-ის
აგებადი spread ფიქსირებულ operation count-ზე ყველაზე დიდია:

    20           19       6              3..5        2                            5            5

ყველაზე დიდი `peak_live`, რომელიც `n` ფოთლის მქონე ხეს შეიძლება ჰქონდეს, არის `floor(log2(n)) + 1`, და
sweep ადასტურებს, რომ ზღვარი ყოველ წერტილში მჭიდროა. ამ instruction set-ს აქვს `16` არქიტექტურული `xmm`

მეტ რეგისტრს მოითხოვდა.** მეოთხე ღერძი ვერ იმოქმედებს ვერცერთ expression-ზე, რომელსაც ადამიანი დაწერდა,
და probe-ის null შედეგი ამ corpus-ის შემთხვევითობა არ არის.

## ინტერპრეტაცია

- **Representation-ის სხვაობა გადარჩება `-O2`-ს მანქანურ კოდში, და სწორედ ეს არის card-ის ის ნაწილი,
  რომელიც მეორდება.** `16` object-იდან `0` კომპილირებს თავის ორ writing-ს ერთსა და იმავე
  ინსტრუქციებად `-O2`-ზე; `16`-იდან `8` კი `-O3 -ffast-math`-ზე. ეს ზუსტი მტკიცებაა, რომელშიც არც
  floor არის და არც გამეორებების რაოდენობა, და ის დამოუკიდებლად იქნა ხელახლა გამოყვანილი. ყველაფერი
  ქვემოთ timing-ის მტკიცებაა და უფრო რბილი.
- **პროექტის operation count ორ writing-ს უკუღმა ალაგებს ყოველთვის, როცა division-ები განსხვავდება.** ეს
  card-ის ყველაზე ძლიერი დადებითი timing შედეგია და ის ორჯერადია და არა დამრგვალების ცდომილება, და
  მართლდება `5` გაშვებიდან `5`-ში ოთხი level-იდან სამზე. ნებისმიერი ranking 0034-ში, 0037-ში, 0042-ში,
  0044-ში ან 0049-ში, რომელიც division count-ით განსხვავებულ writing-ებს ადარებს, ზომავს იმას, რასაც
  hardware ისე არ ახდევინებს, როგორც დათვლა გულისხმობს.
- **`peak_live` ღერძია ის, რომელსაც ნდობა არ უნდა.** ყველა inversion-ის დაახლოებით სამი მეოთხედი მასზეა
  ყოველ გაშვებაზე — `35`-იდან `24`, `34`-იდან `26`, `39`-იდან `28` — ყოველ optimisation level-ზე, და
  აგებული probe აჩვენებს, რომ მიმართულება არასწორია თანაბარ operation-სა და თანაბარ depth-ზე. ღერძი
  ხის რეალური თვისებაა და რეგისტრზე მოთხოვნის რეალური ზღვარი, მაგრამ ამ მანქანაზე, იმ სიდიდეებზე,
  რომლებსაც ნებისმიერი expression აღწევს, ის სიჩქარეს არ პროგნოზებს და მისი ნიშანი საიმედოდ ის არ არის,
  რომელსაც frontier აძლევს.
- **`depth` ღერძი მეტალთან შეხებას სხვა ნებისმიერზე უკეთ უძლებს.** მასზე `2`-დან `5`-მდე inversion-ია
  `peak_live`-ის `24`-დან `28`-მდე-ს წინააღმდეგ, და აგებული probe მას გადამწყვეტად და განმეორებადად
  უხდის — სანამ `-ffast-math` graph-ს reassociate არ გააკეთებს და ღერძი შესრულებულის აღწერას არ
  შეწყვეტს.
- **Representation-ის არჩევანი compile-time გადაწყვეტილებაა, და optimisation level representation-ის
  ნაწილია.** თექვსმეტწევრიანი ჯამის იგივე ორი writing `O2`-ზე dependent-chain რეჟიმში `160%`-ზე მეტით
  არის დაშორებული და `O3fast`-ზე განურჩეველია. Router, რომელიც representation-ებს ალაგებს იმ flag-ების
  დასახელების გარეშე, რომლებზეც ისინი კომპილირდება, თავისუფალი ცვლადით ალაგებს.
- **ამ card-ის ყოველი ეფექტი harness-ით არის შეკუმშული და ჭეშმარიტი სტრუქტურული სხვაობები უფრო დიდია.**
  Loop-ის საკუთარი ფასი `O2`-ზე throughput რეჟიმში არის დაახლოებით `0.256` ნანოწამი თითო step-ზე,
  ზღვრული `0.061` ნანოწამი თითო operation-ის წინააღმდეგ, ასე რომ სამ-operation-იანი expression უფრო მეტ
  harness-ს ატარებს, ვიდრე არითმეტიკას. ყოველი აქაური პროცენტი ქვედა ზღვარია.
- **ამ harness-იდან timing-ის ციფრი განაწილებაა და არა მნიშვნელობა, და card ახლა ამას ყველგან ამბობს.**
  `8` survival უჯრიდან `0` გამეორდა შვიდ გაშვებაზე; მთავარი inversion-ების რაოდენობა `2`-სა და `4`-ს
  შორის მოძრაობდა სამზე; `32` probe უჯრიდან `7`-მა პასუხი შეიცვალა ხუთზე. ის ეფექტები, რომლებიც ამ
  ყველაფერს გადაურჩა — division, depth და ორი დასახელებული inversion — არის ის, რისი მიხედვითაც ღირს
  მოქმედება, დანარჩენი კი მოცემულია თავისი spread-ით და არა დარანჟირებული.
