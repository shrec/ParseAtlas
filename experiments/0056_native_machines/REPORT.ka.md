## რა აშენდა

`src/parseatlas/native_machines.py`. ერთი generator გამოსცემს machine-ს world-ისთვის, ასე რომ world
არის **მონაცემი generator-ისთვის და კონსტანტა machine-ისთვის**. მისგან სამი ვარიანტი გამოდის, და
მესამე არის ის control, რომელიც პირველ ორს წასაკითხს ხდის:

```text
levels    one function per precedence level, unrolled.  No Grammar object, no dictionary, and the
          binding powers do not appear at all - they have become the call structure.
climb     the table-driven loop with its lookup partially evaluated away: one recursive function,
          the operator literals and the integer powers all constants of the code.
lookup    the same single function with the powers read from an injected POWERS dictionary at run
          time.  Its source contains NO world-specific text, so one compilation serves all 25.
```

"native"-ის განსაზღვრება test-ით არის უზრუნველყოფილი და არა მტკიცებით: native machine-ის emitted
source-ში **ერთადერთი subscript ნებისმიერ ადგილას არის token array-ში**, ასე რომ არცერთი სახელის
table არ იკითხება run time-ზე.

ხუთი არქიტექტურა შედარებულია, ერთსა და იმავე string-ებზე, ერთი და იმავე მნიშვნელით:

| არქიტექტურა | რა არის | ერთჯერადი ღირებულება |
|---|---|---|
| `native_levels` | level-unrolled machine, generated თითო world-ზე | `1` compilation თითო world-ზე |
| `native_climb` | partially evaluated climb machine, generated თითო world-ზე | `1` compilation თითო world-ზე |
| `table` | `parseatlas.parser.parse` ზუსტად ისე, როგორც პროექტი აწვდის | არცერთი; ის თავის table-ს ყოველ გამოძახებაზე აშენებს |

## კითხვა 1 - capability

**გამოცხადებულია გაზომვამდე: capability-ის სხვაობა არ არსებობს.** conversion, რომელსაც ხის
თვითნებურად გადაწერა შეუძლია, ყოველ ხეს აღწევს, ამიტომ ორივე არქიტექტურა ზუსტად ერთსა და იმავე ხეთა
სიმრავლეს აღწევს. პატიოსანი კითხვები არის ღირებულება და სისწორე, და სამი რამ იზომება და არა
მტკიცდება.

**`25` world იღებს ზუსტად ერთსა და იმავე string language-ს.** registry-ის ყოველი grammar აღწერს
`primary (operator primary)*`-ს ფრჩხილებით; მხოლოდ ხე განსხვავდება. `2750` მიღების შემოწმებაზე
(`110` string x `25` world) და `250` უარყოფის შემოწმებაზე (`10` გამოცხადებული malformed string x
`25` world) არის `0` ჩავარდნა ორივე მიმართულებით. არცერთ world-ს არ შეუძლია გამოხატოს string,
რომელსაც სხვა world ვერ წაიკითხავს.

**conversion-ს რეალური ვალდებულება აქვს, და აშკარა იმპლემენტაცია მას არღვევს.** conversion, რომელსაც
მხოლოდ ჩვეულებრივი parse-ის *ხე* მართავს, არასწორია: ხე არ იმახსოვრებს, რომელი ქვე-გამოსახულება იყო
ფრჩხილებში, ამიტომ მას არ შეუძლია განასხვაოს `(a * b) + c` და `a * b + c` - ეს ერთი და იგივე `G0`
ხეა - და ისინი აუცილებლად დაშორდებიან იმ world-ში, სადაც `+` უფრო მჭიდროდ იკვრება, ვიდრე `*`.
გაზომილი იმავე audit-ის გავლით, საიდანაც გამოქვეყნებული agreement-ის რიცხვი მოდის, bracket-blind
conversion არასწორია `2750` უჯრიდან `498`-ში, **ყველა `25`** world-ში, მაშინ როცა native და lookup
სვეტები `0`-ზე რჩება. ამიტომ სწორ conversion-ს სჭირდება front end, რომელიც ფრჩხილების სტრუქტურას
ინახავს - მკაცრად მეტი, ვიდრე ჩვეულებრივი parser აწარმოებს.

**და შენახვის შემდეგ conversion აგდებს ყველაფერს დანარჩენს, რაც front end-მა გამოთვალა.** rewrite
კითხულობს token-ების რიგსა და ფრჩხილების საზღვრებს და სხვა არაფერს: ჩვეულებრივი parse-ის შრომა იმის
გადაწყვეტაზე, რომ `a + b * c` იჯგუფება როგორც `a + (b * c)`, flatten-ის მიერ იშლება. ეს არის

შეუძლია.
